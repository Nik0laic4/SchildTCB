## Что это

Schild TCB — исследовательский прототип доверенной вычислительной базы на микроядерной архитектуре. Это **три артефакта, а не один**:

1. **Автономная ОС (bare-metal)**, написанная с нуля на Ada — загрузчик, драйвер NVMe, драйвер e1000e, стек TCP/IP, HTTP-сервер. Работает на ThinkPad T580 и в QEMU. Отвечает на вопрос *«работает ли?»*.
2. **Слой seL4** — микроядро это upstream seL4 (формально верифицированное; локально патченное для x86_64 MCS и поддержки железа, см. [`SEL4_PATCHES_ANALYSIS.md`](docs/technical/SEL4_PATCHES_ANALYSIS.md)), вклад проекта — **root-задача** на Ada/SPARK и несколько демонов. Сеть и хранилище работают **изолированно в Ring 3**, общаясь через IPC. Отвечает на вопрос *«доказано ли?»*.
3. **Методология и корпус кейсов** — построение формальной системы требует большего, чем компилятор; требуется процесс. Мы документируем грабли ИИ-ассистированной формальной верификации, «мёртвые гейты», которые проходили вакуумно, и изоляцию демонов — практический справочник по инженерии высоконадёжных систем ([`textbook_ru.md`](docs/methodology/textbook_ru.md), оригинал · [`textbook_en.md`](docs/methodology/textbook_en.md)).

**Это не продукт, не замена Linux и не сертифицированная система.** Это открытая референсная архитектура и методология построения доверенных вычислительных баз на seL4. Ценность в подходе, assurance-кейсе и задокументированных инженерных решениях, а не в поставке готовой к использованию ОС.

## Метод и роли

Репозиторий сделан задокументированным **человеко-машинным конвейером**, а не одиночной разработкой:

- **Автор (человек)** — архитектура, требования, аудит-реестр и контроль; держит границу Tier A и все assurance-claims.
- **ИИ-агент** — генерирует код, правит контракты, ищет дефекты; ничего не проходит мимо гейтов и ревью человека.
- **SPARK/gnatprove** — неподкупный оракул; `not-proved: 0` — это машинный факт, а не заявление.

Правила конвейера («конституция ИИ-агента»), модель эскалации и разобранные кейсы (например, H61 — баг с misaligned стеком, который прувер не мог поймать) — в [`docs/methodology/`](docs/methodology/).

## Ключевые характеристики

- **Формальная верификация** — канонические числа SPARK Level 4 генерируются из `obj/proof/metrics.json` (см. [`ASSURANCE.md`](docs/technical/ASSURANCE.md) §2.2):

<!-- METRICS:START (generated by scripts/generate_metrics.py — do not edit) -->
**SPARK metrics** (commit `b874871`, 2026-11-23): **189 прогнано** · **179 в proof-наборе** (133 доказано · 44 skipped · 2 no-output) · **10 scaffold исключено** · **0 непроверенных VC**.

Схема учёта: `swept` = все модули; `in_proof` = `swept` − `scaffold_excluded`; `proved + skipped + no_output + not_proved` = `in_proof`. Источник: `obj/proof/metrics.json`.
<!-- METRICS:END -->

Ещё 8 proof-юнитов root-задачи (root-задача + 7 библиотек/моделей — политика MLS, модели capability/процессов/firewall, загрузчик, HM/launch-модели, watchdog) доказаны.
- **Изолированная периферия** — сеть (e1000e → I219-V) и хранилище (NVMe + SchildFS) работают в изолированном Ring-3 **NetServer**; сбой там не достигает доказанного ядра.
- **MLS Bell-LaPadula** — 5 уровней в слое seL4 (Public..Top_Secret), 4 в bare-metal ядре.
- **Сдерживание сбоев** — сбой драйвера перехватывается и изолируется без перезагрузки платформы.
- **Загрузка на реальном железе** — ThinkPad T580 (32 ГБ) и QEMU.
- **Уроки из окопов** — сборник-учебник кейсов: как полностью верифицированный модуль HMAC молча завис из-за смещения стека на 8 байт, почему тавтологический контракт прошёл все гейты, и мёртвый гейт, который не мог упасть. [`textbook_ru.md`](docs/methodology/textbook_ru.md) / [`textbook_en.md`](docs/methodology/textbook_en.md).

## Архитектура

| Слой | Назначение |
|------|-----------|
| `01_hardware` | MMU, APIC/IOAPIC, NVMe, e1000e, SMP, таймер PIT |
| `02_security` | MLS Bell-LaPadula, модель возможностей, шлюз IPC, файрвол |
| `03_crypto` | AES-NI, SHA-256, HMAC-SHA256 (FIPS 198-1), ГПСЧ |
| `04_userland` | SchildFS/VFS, сокеты, сетевой стек (ARP/IPv4/TCP/UDP/HTTP) |

## Статус верификации (честные границы)

| Уровень | Код | Утверждение |
|---------|-----|-------------|
| **A — Доказанное ядро** | политика MLS, модель возможностей, таблица процессов, вердикты файрвола | *Формально верифицировано* (SPARK, 0 непроверенных VC) |
| **B — Изолированная периферия** | e1000e, NVMe, сетевой стек | *Сдержано* — компрометация не достигает уровня A |
| **C — Каркас** | крипто фильтра пакетов, полные правила файрвола | *Не реализовано в этой сборке*, явно помечено |

Драйверы (NVMe, e1000e, сетевой стек) **не доказаны** и не заявляются таковыми — у аппаратуры нет формальной спецификации. Вместо этого они изолированы в отдельные домены.

> **Примечание про `schild_firewall`:** он разделён по tiers — **вердикты** пакетов (token-bucket limiter) — Tier A и доказаны, а полный **ruleset/крипто** — Tier C-каркас (не реализован). Это осознанная граница, а не отсутствующий файрвол.

Известные ограничения upstream (не в этом коде):

- **IOMMU (VT-d)** — experimental/flaky upstream (спорадическая гонка scheduling-context на x86_64 MCS). DMA-изоляция отложена.
- **SMP** — `KernelMaxNumNodes` форсируется в 1 на x86_64 **MCS** (ограничение upstream).
- **x86_64 MCS** формально верифицирован **слабее, чем ARM MCS** (официальный статус upstream).

## Порт ARM64 (ветка `arm64`)

Ветка **`arm64`** нацелена на **Raspberry Pi 4B** (BCM2711) — **формально верифицированную AArch64**-платформу seL4 (4× Cortex-A72, SMP, отладка по UART):

- Полный цикл в QEMU работает: ELF loader → ядро seL4 → root task → вывод по UART.
- **virtio-net в QEMU** — валидирован end-to-end: ARP → ICMP → DHCP → TCP/HTTP → TCP-сервер → DNS, с split-ring кольцом дескрипторов, IRQ через seL4 Notifications (блокирующий `seL4_Wait` в waiter-треде) и драйвером + протоколом в **изолированном child-домене** со своим CSpace.
- Инструментарий: QEMU aarch64, `gcc/g++-aarch64-linux-gnu`, `gnat-aarch64`, `repo`, `protoc`, `dtc`.
- У Raspberry Pi **нет SMMU**, поэтому DMA-изоляция на этой платформе вне скоупа.

См. [`src/schild_core/arm64/README.md`](src/schild_core/arm64/README.md).

## Сборка (x86_64)

**Быстрый старт (Docker, без установки тулчейна):**

```bash
docker build -t schild-tcb .
docker run --rm -v "$PWD":/repo schild-tcb    # сборка + SPARK-проверка (зелёный = "proof passed")
```

Требования (нативно): GNAT (Ada/SPARK 2022) + gprbuild (рекомендуется Alire `gnat_native` 14.2.1), grub-mkrescue, QEMU.

```bash
cd src/schild_core

# Автономное ядро (bare-metal)
./build.sh

# Интеграционный слой seL4 (root-задача Ada/SPARK), QEMU
SEL4_PRIMARY=1 ./build.sh

# Формальная верификация
bash scripts/verify.sh          # демоны root-задачи, SPARK Level 4
bash scripts/prove_kernel.sh    # полный прогон ядра (180 модулей)

# Прогон в QEMU
SKIP_BUILD=1 SEL4_PRIMARY=0 bash scripts/run_tests.sh
```

## CI (GitHub Actions)

- **Push / PR в `master`** → автоматически выполняются `build` (bare-metal ядро + ISO) и `verify` (8 proof-юнитов root-задачи, SPARK Level 4).
- **Вручную** (`Actions` → `CI` → *Run workflow*) → задача `prove-full` выполняет полное доказательство 180 модулей на SPARK Level 4 (`scripts/prove_kernel.sh`) и загружает `obj/proof/report.txt` как артефакт.
