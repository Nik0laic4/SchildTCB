**Версия:** v1.1.0-audit (§12 заменяет конфликты в §3–§11 до инлайн-слияния)
**Дата:** 2026-11-03
**Владелец:** Ирганов А.Н.
**Статус:** живой документ. Согласован с [`ASSURANCE.md`](ASSURANCE.md) (модель доверия),
[`SECURITY.md`](SECURITY.md) (покомпонентные claims), [`ARCHITECTURE.md`](ARCHITECTURE.md)
(спецификация). Этот документ — **вход** в усиление контрактов: каждое
Tier-A свойство безопасности из §7 должно в итоге стать SPARK-контрактом.

> **Честная оговорка о scope.** Это модель угроз для исследовательского
> прототипа. Она следует *структуре* оценки рисков безопасности DO-326A, не
> заявляя сертификационного соответствия. Цель — точные, покомпонентные,
> механически проверяемые claims, а не широкий ярлык «high-assurance».

## 1. Назначение

Этот документ отвечает на четыре вопроса, по порядку:

1. **Что мы защищаем?** (§2 Активы)
2. **Кто атакует и насколько способен?** (§3 Модель нарушителя)
3. **Что их останавливает?** (§4 Границы доверия, §5 Допущения, §7 таблица)
4. **Что остаётся после всех защит?** (§8 Остаточные риски)

Он также фиксирует **что мы принимаем на веру** (§9 аксиоматика seL4) и **как
закрываются оставшиеся пробелы** (§10 усиление контрактов).

### 1.1 Связь со стандартами

| Артефакт | Стандарт | Статус |
|----------|----------|--------|
| Эта модель угроз (оценка рисков безопасности) | DO-326A / DO-356A | структура соблюдена; **не** сертификационный артефакт |
| SPARK-доказательства | DO-333 (дополнение по формальным методам) | в процессе; Level 4 на доказанном ядре |
| Критичность безопасности / DAL | DO-178C | **не целевой** — одиночный исследовательский прототип не заявляет соответствия DO-178 |

## 2. Активы (A1–A6)

| Актив | Что это | Ключевое свойство безопасности | Tier |
|-------|---------|-------------------------------|------|
| **A1 — Доказанное ядро** | MLS-политика, модель capability, таблица процессов, вердикты firewall | конфиденциальность + целостность (математически enforced) | A |
| **A2 — Изолированная периферия** | NetServer: e1000e / NVMe / стек TCP-IP (ARP, IPv4, TCP, HTTP) | доступность через *containment* — его компрометация не должна распространяться | B |
| **A3 — Рантайм TCB** | ядро seL4 + root-задача Ada + доверенные швы (syscall-shim, C-runtime, `boot.S`) | целостность всей системы | ring 0 + root |
| **A4 — Аудит-журнал** | `Schild_Audit_Logger` ring-buffer с фильтром по severity | целостность + неотказуемость | A |
| **A5 — Путь загрузки и обновления** | A/B-образы, `Schild_Boot_Manager`, boot-счётчик, rescue-слот | целостность + доступность | lockout ✅ (W9.1); пробел целостности — нет signed boot (§8) |
| **A6 — Платформа и устройства** | CPU, MMU, APIC/GIC, NIC, NVMe, DMA-движки | доступность + целостность | (DMA вне scope) |

Каждый актив — *причина* существования класса нарушителя в §3. Связка
«актив → нарушитель → защита → проверка» замкнута в §7.

## 3. Модель нарушителя

Четыре **класса** нарушителя (P1–P4) определяют *кто* в scope. Одна **ось
способностей** (каскад ИИ-агентов) применяется поверх P1–P4 и определяет
*насколько способен* атакующий — это **не** пятый класс.

### 3.1 Классы в scope

| Класс | Описание | В scope? |
|-------|----------|----------|
| **P1 — Удалённый сетевой атакующий** | Досягает только открытую поверхность: стек TCP/IP (HTTP-сервер). Без учётных данных, без локального доступа. | да — основной |
| **P2 — Скомпрометированный Tier-B домен** | Уже имеет точку опоры внутри изолированного драйвера/стека (баг проэксплуатирован). Пытается добраться до ядра или других доменов. | да — нарушитель «containment» |
| **P3 — Злонамеренная / скомпрометированная периферия** | DMA-устройство (NIC, NVMe), которое лжёт или пишет в память напрямую. | проанализирован, **не полностью митигирован** (§8) |
| **P4 — Атакующий с локальным доступом к сборке/развёртыванию** | Может подменить образы, писать слоты обновления, переключить boot-счётчик. | частично — rollback/злонамеренное обновление (§8); полный supply-chain **вне scope** |

### 3.2 Каскад ИИ-агентов (ось способностей, поверх P1–P4)

Автономные ИИ-агенты (одиночные или мультиагентные «каскады») не создают
новую поверхность атаки — они **умножают способности** существующих классов,
снижая стоимость, время и навык почти до нуля и связывая несколько багов в
один эксплойт.

Следствия, формирующие эту модель угроз:

1. **Каждая недоказанная строка считается уже эксплуатируемой.** Баги
   memory-safety и логики в C-коде (`net_test.c`, `sel4_mmio.c`,
   `sel4_stubs.c`, `runtime_stubs.c`) и `SPARK_Mode => Off` Ada-драйверах
   считаются найденными и превращёнными в оружие. «Никто это не найдёт» — не
   валидное допущение.
2. **Обфускация мертва; механически проверяемые защиты — нет.** Формальное
   доказательство и изоляция на уровне ядра — единственные контроли, которые
   *не* деградируют по мере ускорения и умнения атакующего. Это ровно
   разделение Tier A / Tier B.
3. **Реактивное патчение слишком медленно.** Для прототипа ответ должен быть
   *архитектурным* (изолировать недоказанное), а не *реактивным* (патчить
   после эксплойта).

**Итог:** ось ИИ *усиливает* аргументы за (a) удержание `pragma Assume` на 0,
(b) доказательство самих security-свойств, а не только абстракции, и
(c) трактовку границы containment Tier-B как основного контроля всего
недоказанного кода.

## 4. Границы доверия

| # | Граница | Что пересекает | Чем enforced |
|---|---------|----------------|--------------|
| **TB1** | ring 0 (ядро seL4) ↔ ring 3 (root-задача + домены) | только syscall ABI | ядро seL4 (VSpace / CSpace / capabilities) |
| **TB2** | root-задача ↔ NetServer / MLS-server | IPC-сообщения + endpoint-badges + notifications | capabilities seL4 (права `Send`/`Recv`/`Grant`), проверки badge |
| **TB3** | Tier A ↔ Tier B | **только контракты** (золотое правило) | архитектура: Tier A зависит от Tier-B *spec*, никогда от Tier-B *body* |
| **TB4** | платформа ↔ всё остальное | MMIO / DMA / прерывания | **слабейшая** — сегодня нет IOMMU/VT-d (см. §8) |

TB1–TB3 реальны и механически проверяемы. TB4 — открытая граница: без
DMA-изоляции злонамеренное устройство (P3) может читать/писать любую
физическую память, включая ядро и root-задачу.

## 5. Допущения (каждое с последствием нарушения)

| # | Допущение | Что случится при нарушении |
|---|-----------|---------------------------|
| **AS1** | Ядро seL4 (апстрим + локальные патчи) корректно и enforced свою capability/VSpace-модель. | Полная компрометация — ничего выше не выживает. Это корень доверия. |
| **AS2** | Железо ведёт себя по спецификации (CPU, MMU, APIC/GIC, без rowhammer/glitch-атак). | Все гарантии доказательства и изоляции аннулируются (физические/side-channel, вне scope §6). |
| **AS3** | Тулчейн (GNAT, GCC) и пруверы (Alt-Ergo/CVC5/Z3) корректны. | SPARK-доказательство аннулируется. |
| **AS4** | Цепочка загрузки до ядра (Multiboot2-загрузчик / прошивка) не контролируется атакующим. | Атакующий подменяет ядро или root-задачу до загрузки — ничего не восстановит. |
| **AS5** | Syscall-шов (`Schild_Sel4_Syscall` + C-шимы) корректно кодирует ABI seL4 (номера syscall, кодирование message-info, MR/cap-слоты). | Баг шва даёт домену выйти из CSpace/VSpace. Протестирован в рантайме, не доказан (§9). |

Каждое допущение — *цена* соответствующего claim. Если одно нарушено, claims
из §7, зависящие от него, аннулируются — это заявлено, а не скрыто.

## 6. Вне scope (с обоснованием)

| Пункт | Почему вне scope |
|-------|------------------|
| DMA-изоляция (IOMMU/VT-d) | апстрим x86_64 MCS экспериментален/flaky; Raspberry Pi 4 не имеет SMMU. **Наивысший остаточный риск (§8).** |
| SMP на x86_64 MCS | апстрим заставляет `KernelMaxNumNodes = 1` на x86_64 MCS. |
| Физические атаки (probe, glitch, cold boot, rowhammer) | нет модели угроз для кремния; допущение AS2. |
| Side-channels (Spectre/Meltdown/…) | IBRS *пытается* включиться при загрузке, не полная митигация. |
| Supply chain (компилятор, железо, апстрим seL4) | вне досягаемости одиночного прототипа; допущение AS3. |
| Доступность/DoS самого Tier-B домена | по дизайну containment означает, что *ядро* выживает — а не что изолированный домен всегда работает. |
| Полная сертификация DO-178C | не цель одиночного разработчика (см. §1.1). |

## 7. Угроза → механизм → tier → механическая проверка

Это основная таблица. Каждая строка — claim, который должен оставаться
истинным; колонка «проверка» — как он enforced или демонстрируется.

| # | Угроза (нарушитель) | Механизм защиты | Tier | Механическая проверка |
|---|---------------------|-----------------|------|-----------------------|
| T1 | P1 (+ИИ) удалённый memory-safety эксплойт TCP/UDP-парсера (в т.ч. ИИ-генерируемый UAF/overflow) | **SPARK Level 4 на парсерах** (`Parse_Tcp`/`Parse_Udp`/`Parse_Arp`/`Parse_Ipv4`/`Validate_Tcp_Checksum`, все `On`) + домен защиты seL4 + fault endpoint | A + B | `prove_kernel.sh` (`not-proved: 0`) + `[CONTAINMENT] core alive after fault` |
| T2 | P2 скомпрометированный домен эскалирует к Tier A через IPC | модель capability: mint / copy / retype / revoke / derivation + endpoint-badges | A | SPARK Level 4 на `schild_cap_space` (`prove_kernel.sh`) |
| T3 | P1/P2 обход MLS (read-up / write-down / control-up) | `Schild_MLS_Policy` + проверки уровней `schild_process_manager` | A | `verify.sh` / `prove_kernel.sh`; QEMU MLS 8/8 |
| T4 | P2 (+ИИ) uninitialized read / integer overflow / out-of-bounds в ядре | SPARK: нет uninit-read, ограниченные диапазоны, суженные index-типы (Phase-1 фиксы) | A | `prove_kernel.sh` → `not-proved: 0` |
| T5 | P2 вешает root-задачу (доступность) | бюджеты MCS CPU + fault-timeouts | A/B | `seL4_Fault_Timeout` (QEMU MCS-тест) |
| T6 | P3 DMA-запись от злонамеренного NIC/NVMe | **сегодня ничего** (нет IOMMU) | — | остаточный риск (§8) |
| T7 | P4 rollback / злонамеренное обновление слота | `Schild_Boot_Manager` SHA-256 + lockout boot-счётчика (ограниченные retry → lock слота) | — | остаточный риск — нет signed boot (§8) |
| T8 | P1 (+ИИ) эксплойт C-шимов/стека (`net_test.c`, `sel4_mmio.c`, `runtime_stubs.c`) | **нет memory safety** — containment единственный backstop | B | `[CONTAINMENT] core alive after fault` |
| T9 | P4 (+ИИ) supply-chain (отравленный апстрим/тулчейн) | нет | — | вне scope (§6) |

**Примечание для чтения:** сетевые парсеры T1 (ARP / IPv4 / ICMP / UDP / TCP)
теперь **формально memory-safe** — SPARK Level 4, `not-proved: 0` (W10). C-шимы
и драйверы (`net_test.c`, `sel4_mmio.c`, `e1000e`, `nvme`) остаются **не**
memory-safe — для них (T8) containment единственный backstop. T2–T4 — формальное
доказательство; T1 теперь и доказательство (парсер), и изоляция (драйвер / C-шим).

## 8. Остаточные риски (честно, после всех механизмов)

Это риски, остающиеся даже когда все проверки §7 зелёные:

1. **Нет DMA-изоляции (наивысший).** Злонамеренное DMA-устройство (P3) может
   читать/писать произвольную физическую память, включая ядро и root-задачу.
   IOMMU/VT-d ожидается в апстриме; Raspberry Pi 4 не имеет SMMU. До тех пор
   «изолированная периферия» означает *process*-изоляцию, а не *bus*-изоляцию.
2. **Недоказанный C-код считается эксплуатируемым.** `net_test.c`,
   `sel4_mmio.c`, `sel4_stubs.c`, `runtime_stubs.c`, `interrupt_handlers.c`,
   `hw_io.c` memory-unsafe и не в proof-наборе. Containment (T8) — единственный
   backstop.
3. **Контракты доказывают абстракцию, но не всегда полное security-свойство.**
   Это *известный* пробел, который закрывает следующая фаза (§10). Сегодня
   «proved» значит «spec модуля доказан», а spec может быть слабее
   end-to-end security-свойства (например, «нет read-up через *все* IPC-пути»).
4. **Нет signed boot / аппаратного корня доверия.** `Schild_Boot_Manager`
   SHA-256 детектит *повреждение*, а не *злонамеренность*: атакующий, который
   может писать слот обновления (P4), может написать и валидный хэш. Rollback
   и злонамеренное обновление остаются открытыми. Boot-счётчик W9.1 ограничивает
   *доступность*-ущерб от постоянно плохого слота (N retry → lock слота →
   brick/recovery), но сам счётчик доверен ровно настолько, насколько доверен
   образ, с которым он поставляется — то же ограничение, нет HWRoT.
5. **x86_64 MCS формально верифицирован слабее ARM MCS** (статус апстрима).
6. **Запатченный seL4.** Локальные патчи изменяют формально верифицированное
   ядро; апстрим-доказательство переносится лишь частично (§9).
7. **Watchdog/DoS.** Аппаратный watchdog (будущая работа) восстанавливает из
   зависаний, но сам является усилителем DoS, если атакующий может триггерить
   зависания; это последнее средство *после* containment, а не замена ему.
8. **Повторное использование PID без задержки (CVE-2026-SCHILD-02 #005).**
   Process IDs переиспользуются немедленно при завершении без окна охлаждения,
   так что signal или IPC-сообщение, предназначенное только что завершённому
   процессу, может достичь несвязанного преемника, переиспользовавшего тот же
   PID. Митигировано (M1, 2026-11-08): монотонная генерация PID на слот
   (`PID = Slot + Generation × Max_Processes`) закрывает немедленное
   переиспользование; capability-based identity остаётся долгосрочным
   предпочтением.

## 9. Аксиоматика seL4 (что принимается на веру)

Следующее **доверяется, не пере-доказывается**, и должно быть перечислено явно:

- **Корректность апстрим-ядра seL4.** seL4 имеет machine-checked доказательство
  функциональной корректности (сильнейшее для верифицированной ARM-конфигурации;
  x86_64 MCS слабее — апстрим). Мы принимаем это как корень доверия.
- **Локальные патчи.** `patches/` содержит модификации ядра
  (`seL4-smap.patch`, `seL4-object-zeroing.patch`, `seL4-framebuffer*.patch`
  (×3), `seL4-max-num-drhu.patch`, `seL4-bootinfo-8k-untyped.patch` и
  `seL4-load-image-above-kernel.patch`). Они изменяют верифицированное ядро;
  **reviewed, но не re-proven**, так что перенесённая гарантия частична. Это
  реальное, признанное ослабление. Полный анализ, классификация рисков и
  стратегия минимизации (root-задача как ELF-child, собственный UART-драйвер,
  миграция Kconfig, апстрим-обновления) — в
  [`SEL4_PATCHES_ANALYSIS.md`](SEL4_PATCHES_ANALYSIS.md).
- **Syscall-шов.** `Schild_Sel4_Syscall` (spec `On`, body `Off`) и C-шимы кодируют
  ABI seL4 (номера syscall, раскладка message-info, MR/cap-слоты). Отображение
  Ada-контрактов в фактический ABI доверяется и тестируется в рантайме, не доказано.
- **C-runtime и вход.** `runtime_stubs.c`, `interrupt_handlers.c`, `hw_io.c`,
  `boot.S` — ring-0 доверенный код, только рантайм-тестируемый.

Любая будущая работа, затрагивающая эти швы, должна обновить этот раздел.

## 10. От модели угроз к более сильным контрактам (следующая работа)

Этот документ — **вход** в фазу усиления контрактов. Метод:

1. Для каждой Tier-A строки §7 (T2–T4) вывести **точное** security-свойство.
   Примеры: «capability никогда не минтится в слот без валидного родителя»,
   «никакой IPC не пересекает границу уровня вниз», «никакой индекс буфера не
   выходит за заявленный диапазон».
2. Перевыразить это свойство как SPARK-контракты (`Pre`/`Post`/`Global` +
   инварианты цикла) и доказать на Level 4.
3. **Правило против удушения.** `Pre` должен принимать *все* легитимные входы;
   `Post` заявляет security-свойство. *Liveness* — что легитимные данные всё ещё
   текут — проверяется рантайм-тестами (QEMU 24/24, KAT), а не доказательством.
4. **Никакой вакуумности.** `Post => True` или невозможный `Pre` ничего не
   доказывает и отклоняется. Проверки вакуумности gnatprove включены.
5. **Никаких escape-hatch.** Держать `pragma Assume` = 0 и без подавления
   `pragma Annotate` (текущее состояние: оба 0). Если шов действительно нельзя
   доказать, записать его здесь как доверенную аксиоматику (§9), а не как
   скрытый `Assume`.

## 12. Исправления из аудита v0.4 (2026-11-03) — заменяет конфликты в §3–§11

> **Статус раздела.** Приложен внешним security-аудитом (реестр:
> `START/AUDIT_REGISTRY.md`). Исправления с пометкой C-§N правят §N. Пока §3–§11
> не инлайнены, этот раздел нормативен там, где конфликтует. Это дополнение
> делает THREAT_MODEL v1.1.0-audit.

### 12.1 Исправления к §3 (Модель нарушителя)

**C-§3.1 P4 против AS4.** P4 (локальный доступ к сборке/развёртыванию) и AS4
(цепочка загрузки не контролируется атакующим) несовместимы. AS4 применяется
только к P1–P3. Против P4 целостность загрузки и обновления **не заявляется**
(§8.4 уже признаёт это, но §5 AS4 в одиночку читался вводящим в заблуждение).

### 12.2 Исправления к §4 (Границы доверия)

**C-§4 TB3.** TB3 enforced архитектурой (дисциплина with-clause), а не
механически. Один with-clause, связывающий Tier-B body в Tier A, проходит
доказательство молча. Это процессный контроль, а не механическая проверка.
Tier-B spec, от которых зависит Tier A, — часть TCB и перечислены в §9
(исправлено, AS7). Механическая защита — build-проверка (nm по Tier-A бинарю,
фейл на любой Tier-B символ) — аудит H4.

**C-§4 TB4 (Pi 4).** На Raspberry Pi 4 (bcm2711) нет SMMU, а GENET — это
дополнительный DMA-мастер. P3 (злонамеренная/скомпрометированная периферия)
строго хуже на Pi 4, чем на x86_64. Pi 4 не в текущем scope TCB; DMA-анализ
для Pi 4 — отдельный профиль (§6 исправлено).

### 12.3 Исправления к §5 (Допущения)

**C-§5 AS4.** Scope уточнён: применяется к P1–P3, аннулируется против P4.

**AS6 — syscall-шов (новое).** Тело `Schild_Sel4_Syscall` — `SPARK_Mode => Off`
(1767 строк, аудит C10), плюс C-шимы (`schild_sel4_ipc.c`,
`schild_sel4_syscalls.S`, `message_info.c`). Доверяется, не доказан. Отображает
Ada-контракты в ABI seL4. Баг здесь даёт домену выйти из CSpace/VSpace. По §3.2
(ось ИИ) AS6 **считается эксплуатируемым**; при P2 история containment рушится,
если AS6 не держится.

**AS7 — spec Tier B (новое).** Tier A зависит от spec (контрактов) Tier-B
сервисов, которые он вызывает. Эти spec — доверенные аксиомы, перечислены в §9
(исправлено). Скомпрометированное тело Tier B (P2) может нарушить свой
собственный spec, и тогда доказательство Tier A не переносится на работающую
систему.

### 12.4 Исправления к §6 (Вне scope)

**C-§6 Pi 4.** Убрать «Raspberry Pi 4 не имеет SMMU» как обоснование
вне-scope DMA. Заменить на: «Pi 4 не в текущем scope TCB. Когда Pi 4 войдёт в
scope, DMA-изоляцию нужно переанализировать; отсутствие SMMU означает, что P3
строго хуже, чем x86_64, а не что DMA вне scope».

### 12.5 Исправления к §7 (Угроза → механизм → проверка)

**C-§7 T1.** T1 доказан на уровне модулей: `Parse_Tcp`/`Parse_Udp`/`Parse_Arp`/
`Parse_Ipv4`/`Validate_Tcp_Checksum` и `schild_http_core` — L4-доказаны.
Построитель ответа (`Write_Str`, `Write_U32_Dec`) доказан (W11.3). Обработчик
запроса `Handle_Request` (`schild_http_server.adb`, Off) **не** доказан: содержит
рантайм-guard для пути запроса (5..1024), но путь ответа имел unguarded
Pre-нарушение (аудит C23, запатчен 2026-11-03). T1 как написано точен для
парсеров, не для обработчика.

**C-§7 T5.** Бюджеты MCS CPU решают CPU-голодание, но **не** флуд
IPC-сообщений. Высокочастотный P2-отправитель может голодать IPC-бюджет
root-задачи при низкой CPU-стоимости. T5 как написано это не покрывает
(residual R15).

**C-§7 T8.** Разделить:
- **T8a** — Tier-B C-шимы (`net_test.c`, `sel4_mmio.c` в Ring-3 доменах):
  memory-unsafe, containment работает (краш Ring 3, ядро выживает).
- **T8b** — ring-0 доверенный C (`runtime_stubs.c`, `interrupt_handlers.c`,
  `hw_io.c`, `boot.S`): memory-unsafe, **containment не работает**. Баг здесь
  паникует ядро или даёт исполнение Ring 0. Доверяется (§9), считается
  эксплуатируемым по оси ИИ. Больший residual, чем T8 изначально писал.

**T10 — DDE/GENET-драйверы (новое).** Когда DDE-импортированные драйверы или
GENET-драйвер войдут в дерево, они Tier B (Ring 3, containment). Spec сервиса
драйвера доверяется (AS7). Tier A должен быть независим от тела драйвера —
enforced процессным контролем TB3 плюс build nm-проверкой (аудит H4).

**T11 — Watchdog-усилитель DoS (новое).** Watchdog — восстановление последнего
средства, не замена containment. Если P1 может триггернуть зависание NetServer,
срабатывающее watchdog, P1 получает перезагрузку по требованию. Требование:
срабатывание watchdog гейтится политикой в root-задаче, rate-limited, и **не
должно** срабатывать для contained-фолтов (contained-фолт обрабатывается fault
endpoint; watchdog — только для неотвечающих, но не-фолтнутых состояний).

**T12 — Health check через Tier B (новое).** `Health_Status`
(Network_Up, MLS_Valid) читается из Tier-B сервисов. Скомпрометированный Tier B
возвращает фейковый «здоров»; `Commit_If_Healthy` коммитит; lockout не
срабатывает; защита доступности против постоянно плохого слота обходится.
Tier-A claim (надёжность загрузки) зависит от правдивости Tier B. Аудит C9.

**T13 — Общий DMA-фрейм через границу доверия (новое).** Общий 4 КБ фрейм на
`0x520000` замаплен и в root-задачу, и в NetServer. Если root-задача читает
данные, записанные NetServer (путь RX-log сейчас так делает), а NetServer
скомпрометирован (P2), root-задача доверяет фейковым данным. Правило дизайна:
root-задача пишет для TX (безопасно), читает для RX-log только с явным
признанием доверия, либо переносит RX-log в структурированный IPC. Аудит C8.

### 12.6 Исправления к §8 (Остаточные риски)

Дополнительные residuals:

**R9 — Ring-0 C, нет containment.** `runtime_stubs.c`, `interrupt_handlers.c`,

### 12.8 Исправления к §10 (Методология)

**C-§10 анти-вакуумность.** Проверка вакуумности gnatprove ловит

§10 пункт 4 («Post => True отклоняется») должен гласить: отклоняется
человеческим ревью, а не gnatprove.

### 12.10 FS hardening + уточнение модели угроз (аудит v0.7, 2026-11-03)

**Источник:** заметки разработчика + перекрёстная проверка аудита. Половина уже
была в §12; остальное — новое.

**C-§3.2 ось ИИ (конкретизация).** Разделить T1 на T1a (один malformed-пакет,
memory safety парсера — доказан) и T1b (фаззинг на гонки, последовательность
легитимных пакетов, целящая во взаимодействие connection state / parser state).
T1b — сценарий фаззинга ИИ-агентов; не доказан, изолируется Ring-3 изоляцией
NetServer.

**C-§7 T14 (PID reuse).** Перенесено из residual §8.8 в таблицу угроз как T14.
Угроза: P2 шлёт signal или IPC на PID, только что переиспользованный несвязанным
процессом. Статус: **митигировано (M1, 2026-11-08)** — монотонная генерация PID
на слот; capability-based identity остаётся долгосрочным предпочтением. Ведётся
в аудит-реестре как M1.

**C-§7 T15 (подделка FS-метаданных, размещение HMAC-ключа).** FS-метаданные
защищены CRC32 (целостность, не подлинность). P3 (злонамеренный NVMe через DMA)
или P4 (доступ на запись к диску) может подделать и пересчитать CRC32. Переход
на HMAC-SHA256 требует ответа: где живёт ключ? (a) NetServer (Tier B) — P2 может
его прочитать; HMAC защищает только от P3. (b) Root-задача (Tier A) — FS должен
мигрировать в Tier A или проверять HMAC по IPC на блок. (c) Аппаратное хранилище
ключей — недоступно (нет TPM, нет HWRoT). Пока не решено, подделка FS-метаданных
остаётся принятым residual (R18). Аудит H61. **Статус (2026-11-07):** решено —
реализован вариант (a) (H61): HMAC-SHA256 `Hmac_Key`/`Hmac_Tag` в superblock
FS-демона, проверяется при монтировании и обновляется при каждой фиксации
метаданных. Зависание было misaligned стеком FS-демона (aligned-SSE
`movaps`/`movdqa` → #GP), исправлено `andq $-16,%rsp` в `fs_daemon.S`. Ключ
сейчас детерминированный (RDRAND отложен до Блока 3 — линковка RNG-модулей
сдвигает общий ELF, H87). Residual: ключ живёт в superblock (Tier B), поэтому
HMAC аутентифицирует от P3, но не от P2 (ключ читаем Tier B).

**C-§8 R16 (signed boot без HWRoT).** P4 с доступом на запись к диску может
пересчитать SHA-256. Без TPM/HWRoT защиты нет. Принятый архитектурный риск.
Lockout boot-счётчика (W9.1) ограничивает ущерб доступности от плохих слотов,
но не целостность от злонамеренного P4. Это уже заявлено в §8.4; явно
перезаявлено здесь как принятое.

**C-§8 R17 (path traversal — архитектурная митигация).** `SchildFS.Open` ищет по
имени в плоской таблице `Root_Dir (0..15)`; иерархии нет. `GET /../../etc/passwd`
даёт имя, ничего не совпадающее → 404. Закрыто архитектурно, не математически
доказано. Если FS когда-либо получит иерархию каталогов, переанализировать.
Аудит H20 → CLOSED (архитектурно).

**C-§8 R18 (подделка FS-метаданных).** См. T15. CRC32 детектит повреждение, не
подделку. Принято до решения о размещении HMAC-ключа.

**C-§9 (scope патчей).** Уточнить локальные патчи §9: они **не** трогают модель
capability и планировщик. Они **трогают** жизненный цикл объектов
(`seL4-object-zeroing.patch`, security-релевантно: раскрытие uninit-памяти) и
раскладку памяти ядра (`seL4-bootinfo-8k-untyped.patch`). AS8 применяется: если
`object-zeroing` или `bootinfo-8k` вносит дефект, возможно раскрытие памяти
ядра; containment зависит от сохранности модели capability seL4 (которую патчи
не трогают). Аудит H10 остаётся открытым, но его scope сужен: патчи влияют на
жизненный цикл объектов и раскладку памяти, не на модель capability или
планировщик.

**C-§9 уточнение AS6.** Тело `Schild_Sel4_Syscall` Off (1767 строк). Syscall-шов
— крупнейший одиночный доверенный компонент. Митигации в очереди (аудит C4):
memory-safe C-шим, фаззинг отображения ABI, формальная ABI-спецификация. Не
исправлено в v0.1.0.

### 12.11 FS-демон: владение NVMe + MLS + Persist через IPC (аудит v0.23–v0.30, 2026-11-04)

**C-§4/C-§7 — хранилище переезжает из NetServer в выделенный FS-демон (H86).**
FS-демон — четвёртый Ring-3 домен (собственный PML4 + CSpace, слоты +64..+75,
NVMe BAR0 @0x620000). NetServer больше не владеет NVMe — один контроллер, один
владелец; прежняя гонка двух `Init_MMIO` невозможна. FS-демон **Tier B** (как
NetServer): тела `Schild_Schild_Fs` + `Schild_Nvme` `Off`, изолированы процессом,
не доказательством.

**C-§4 золотое правило — восстановлено (H65 CLOSED).** `Persist_Audit_Log`
теперь доходит до SchildFS через IPC (`fs_ep`, op=5 Append), а не прямым вызовом
Tier-A→Tier-B body. Тело FS исполняется в VSpace FS-демона, никогда в VSpace
root-задачи. Residual: общий образ RW (H87) всё ещё позволяет OOB-записи из
любого демона портить общий `.bss` — без изменений с NetServer; ELF-загрузчик
отложен до v0.3.0.

**C-§7 T16 (MLS-классификация FS-демона, H88).** `Role_FS_Server = Top_Secret`
(сток аудита: владеет NVMe + `audit.log`). Enforcement **частичный**:
`Mls_Authorize_Op` выполняется только в `mls_server.c`; IPC не несёт уровень,
поэтому read-up/write-down между демонами держится дисциплиной, а не гейтом.
`Top_Secret`, читающий вниз, BL-разрешён; Internal, пишущий вверх, — нет, записи
пользовательских файлов нужен отдельный путь (или per-object уровни). H88
остаётся открытым (enforcement = Stage 3+).

**C-§7 общий DMA-фрейм (H92).** Общий фрейм @0x52A000 теперь замаплен в три
VSpace (root, NetServer, FS-демон). Доступ сериализован однопоточной
root-задачей (один Call за раз); сегодня конкурентного доступа нет. Если демоны
когда-либо будут работать с фреймом конкурентно, перейти на раздельные offsets
или отдельные фреймы.

**C-§7 containment (H93).** FS-демон — четвёртый домен в
`schild_hm_model`/`schild_launch_model`; fault injection (op=99) → restart →
`[CONTAINMENT] FS daemon contained`, доказано в SPARK (4 домена).

**C-§7 HTTP→FS regression (H91).** После H86 VSpace NetServer больше не мапит
NVMe; статический HTTP-путь теперь возвращает `503` (`Set_Local_FS(False)`)
вместо page-fault. Раздача статических файлов через `fs_ep` — follow-up (H91 (a)).

**C-§7 MCS-бюджет (H90).** FS-демон работает round-robin 5000/5000. Sporadic
(budget < period) **вешает NVMe-mount** (busy-wait polling прерывается mid-DMA;
`Call(init)` не возвращается). Митигация отложена: timeout на Persist Call
(Stage 3+).

### 12.12 Гипервизорный вектор — дополнения модели угроз (2026-11-07, планово)

**Статус:** планируется после Point C. Предусловия: H87 (ELF-загрузчик), Блок 3
(AS6, C1), Assurance Case. Не начинать до H87 — VMM в общем образе RW = OOB в
общий `.bss`.

**T17 — Компрометация VMM (P1/P2).** VMM — Tier B (Ring 3, собственный
PML4/CSpace). Баг virtio (UAF/double-free в descriptor-кольцах) даёт атакующему
контроль над гостевой VM, но containment защищает ядро. Гость внутри VMM — Tier
C (недоверенный, не в TCB). Residual: код VMM memory-unsafe до ELF-загрузчика +
Rust/SPARK.

**T18 — Гость → инжекция в лог хоста (P1 внутри гостя).** Гостевой stdout через
virtio-console в аудит-лог хоста. Злонамеренный гость может подделать формат
аудит-события (`[PASS]`, `[CONTAINMENT]`). Фикс: префикс `GUEST:<vmid>:` +
валидация (длина, UTF-8, без управляющих символов) в Console-демоне; гостевой
лог — отдельный файл, никогда не core audit.log.

**T19 — YAML-эскалация capability (P4 автор конфига).** Декларативный YAML
отображается в invocations seL4. Слабая валидация = privilege escalation
(«дай VM MMIO на NVMe»). Фикс: capability-схема (Tier A, SPARK On): только
FS-демон может NVMe; VMM получает только virtio-NIC/virtio-blk; MMIO-allowlist
по ролям.

**T20 — «Attestation» без HWRoT = measured boot (P4).** Без TPM/secure element
хэш-измерения хранятся в записываемом NVMe — P4 может заменить и хэши, и образы.
Claim должен быть «measured boot (integrity detect)», а не «remote attestation».
Remote attestation требует TPM-quote (T580 fTPM — проверить; Pi 4 — нет).

**R19 — VMM общий образ (P2, блокер).** До H87 VMM делит кадры образа с
root-задачей (`.bss` RW). OOB в virtio = порча глобалов FS-демона/MLS. Поэтому
H87 — жёсткое предусловие гипервизорного вектора, не опционально.

**R20 — MCS Dashboard через tracing-ядро (риск claim).** Чтение использования
sched-context через tracepoints seL4 требует неверифицированной конфигурации
ядра. Claim «verified seL4» больше не держится для этой сборки. Использовать
ручной учёт (демон отчитывается циклами через IPC) или принять ослабление claim.

### 12.13 H88 CLOSED — MLS IPC enforcement + R2 root bypass (2026-11-09)

**C-§5 AS9 (новое доверенное допущение).** `Root task` (role=0, level=4/
Top_Secret) обходит per-IPC MLS-гейт: `Authorize_IPC_Levels(sender_level,
receiver_level, sender_is_root=True) = 1` безусловно. Причина: root-задача —
оркестратор TCB (запускает домены, вызывает init/poll/op=99 на каждом), строгий
BL блокировал бы оркестрацию (root 4 -> Net 1 = write-down). Это осознанная
граница доверия, а не дыра: root-задача в TCB по определению. Некорневые
отправители (role != 0) гейтятся строго.

**C-§7 T21 (новая угроза) — cross-daemon обход IPC.** Без enforcement
скомпрометированный NetServer (P2) мог бы вызвать FS-демон напрямую и
читать/писать Top_Secret-файлы на своём уровне. Гейт H88 блокирует это:
`Authorize_IPC_Levels` запрещает cross-level IPC, если отправитель не root.
Текущий не-root IPC = 0 (H91: HTTP static через 503, нет FS-вызова из
NetServer), так что гейт no-op в рантайме, но механизм на месте для Phase 2
(endpoint пользовательских файлов FS).

**C-§7 T22 (новая угроза) — подделка badge (P1/P2).** Endpoint-badge
устанавливается минтером (root-задачей). Скомпрометированный некорневой демон
не может заминтить badge с `role=0`, потому что у него нет cap root CSpace для
badged endpoint. Подделка badge потребовала бы утечки cap из root CSpace, что
T2 (модель capability) уже покрывает.

**H88 CLOSED (2026-11-09).** Семь шагов:
1. `Authorize_IPC_Levels(Sender_Level, Receiver_Level, Sender_Is_Root)` в
   `schild_mls_policy` (SPARK On, 5 проверок доказано).
2. Константы Role/Level + 4 badged endpoint-слота (`Root_*_EP_Badged_Slot`
   4176-4179) в `schild_sel4_syscall.ads`.
3. Минт badged endpoint в 4 `Launch_*` (badge=4, role=Root).
4. `Call_IPC` в root-задаче переключён на badged-слоты (10 мест).
5. Гейт в 4 `.c`-демонах (mls/net/config/fs), парсинг badge, `SCHILD_EMLSDENIED=13`
   при отказе.
6. Unit-тест `[H88] Authorize_IPC_Levels: root=1 eq=1 up=0 dn=0` (маркер
   run_tests обязателен).
7. Доки.

**Баг сдвига уровней (обнаружен на шаге 6, исправлен).** Первая реализация
использовала 1-based уровни (Root=5), но `Security_Level` — 0-based enum
(Public=0..Top_Secret=4). Уровень 5 попадал в fail-closed guard, все unit-тесты
возвращали 0. Исправлено: Root/MLS/Audit/FS=4, Config=3, Net=1, Guest=0.

**Residuals.** R21 — NetServer(1)->FS(4) read-up блокируется (верно); HTTP static
нужна Phase 2 (endpoint пользовательских файлов level=1, или per-file уровни).
R22 — значения badge не аутентифицированы сверх обладания cap (T22, закрыто T2).
Оба задокументированы, не блокеры.

**Phase 2 (Блок 5, L).** Per-file уровни в FS (level в записи каталога),
отдельный FS-endpoint для пользовательских файлов (level=1), HTTP static через
`fs_ep` (NetServer 1 <-> FS 1 OK, audit 1 -> 4 блокируется). Вне scope H88 Этап 1.

### 12.14 FS self-test + уточнение MLS-политики (аудит 2026-11-15)

**H109 (тихая потеря данных — исправлено).** `Fs_Init` раньше возвращал `St_Ok`
даже когда storage self-test (запись → read-back) падал, так что сломанный FS
выглядел здоровым для root-задачи. Теперь провал self-test возвращает
`St_Io_Error` (`schild_fs_server.adb`), так что `[NVFS] Init OK` означает, что
read-back проверен.

**H111 (вводящий в заблуждение маркер — исправлено).** Self-test read-back
проверял только 2 байта и всё равно печатал `[NVFS] Read-back VERIFY OK`. Теперь
проверяется весь 16-байтовый payload («NovaOS writes!!»).

**H110 (граница сканирования — исправлено).** `Find_By_Start_LBA` теперь имеет
явный `exit when Idx > 13` (Dir_Table 0..13), так что поиск handle не может
выбежать за таблицу каталога.

**M20 (тестовая fault injection).** `op=99` (fault injection crash-containment)
компилируется безусловно в каждом демоне и досягаем любым вызывающим с cap
этого endpoint (сейчас только root). Для продакшена нужно вырезать
(`#ifdef SCHILD_TEST_FAULT` / debug build) или гейтить выделенным test-badge.
Записан как test-only путь; поверхность DoS низкая, потому что только root
держит cap.

**H107 / H88 уточнение политики (residual R23).** MLS-гейт
(`Authorize_IPC_Levels`) — проверка *коммуникационного уровня* (`Can_IPC`,
строгое equal-clearance), а не *per-file / per-operation*: он не различает
`Fs_Open("user.txt")` от `Fs_Open("audit.log")` на одном уровне, ни чтение от
записи. Два конкретных пробела: (a) любой не-root **Top_Secret-пир** (например,
`Audit_Logger`, тоже `Level_Top_Secret`) может `Fs_Delete("audit.log")` —
equal-clearance, гейт проходит; (b) любой домен ниже уровнем не может даже
`Fs_Is_Mounted` — гейт запрещает всё ниже Top_Secret. Для однокуровневого
прототипа это безопасно, потому что единственный вызывающий держит cap FS-EP
как root (role=0, bypass); мульти-уровневый требует per-file уровни +
operation-aware гейт (Phase 2, Блок 5 L).

**R2 root bypass (residual R24).** `sender_role = 0` (root-задача) полностью
пропускает MLS-гейт — обход caller-side, а `Authorize_IPC_Levels` теперь чистый
предикат equal-clearance без ветки обхода (мёртвый аргумент `Sender_Is_Root`
убран). Следствие (должно оставаться явным): **компрометация root-задачи
обходит все MLS-гейты** — enforcement MLS бессмыслен при компрометации root.
Принято с учётом модели угроз (root в TCB, шов trusted-not-proven); residual, не
блокер.
