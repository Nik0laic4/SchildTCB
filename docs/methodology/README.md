# Методология Schild TCB — «конституция» человеко-машинного конвейера

> Язык: Русский (оригинал). Английская версия — по мере выхода статей/arXiv.
> Это **не** технический справочник (он в `docs/technical/`), а изложение
> *процесса*, которым сделан проект. Уникальность SchildTCB — не «ещё один
> seL4+SPARK прототип», а задокументированный конвейер: человек задаёт
> правила и держит границу, ИИ генерирует код, gnatprove служит неподкупным
> оракулом.

## 1. Конвейер: кто что делает

| Роль | Что делает | Держит |
|---|---|---|
| **Человек (автор)** | архитектура, требования, аудит-реестр, правила, контроль коммитов | бинарную границу Tier A, claims («доказано», «безопасно») |
| **ИИ-агент** | генерирует код, правит контракты, ищет слабые места, пишет docs | ничего — всё проходит через gates и ревью человека |
| **gnatprove (оракул)** | доказывает отсутствие runtime-ошибок на Level 4 | безразличную истину: `not-proved: 0` |

Ключевое свойство конвейера: **в конце стоит безразличный оракул**. Ему
нельзя «подсказать» — если контракт не доказан, гейт красный. Именно поэтому
числам в репозитории можно доверять больше, чем словам.

Схема жизненного цикла изменения:

```
идея → правила (AGENT_RULES) → генерация (ИИ) → gnatprove-оракул
     → аудит-реестр (человек) → доки → коммит
```

## 2. Бинарная граница (не «важность», а имя файла)

Самый важный приём — **граница по имени файла, а не по «важности»**. Есть
явный allowlist «Tier A» (ядро TCB: syscall-шов, root task, boot manager,
MLS policy, FS server). Любая правка файла из allowlist — **escalation**
(стоп и вопрос человеку), даже «на одну строку». Файл вне allowlist —
автономно.

Почему по имени: «важность» субъективна и меняется со временем; имя файла —
механический, проверяемый предикат. Это убирает главный провал ИИ — «я
посчитал правку незначительной» — и даёт автоматический pre-commit hook.

## 3. Абсолютные запреты (проверяются hook'ом)

1. `pragma Assume` — один assume аннулирует цепочку доказательств выше.
2. Ослабление `Pre` в Tier A без доказательства.
3. `Post => True` (вакуумный контракт) — gnatprove не ловит, только ревью.
4. Удаление теста / skip / закомментирование проверки.
5. Правка verified-патчей ядра без отдельного ревью.
6. Правка claims-документов (THREAT_MODEL, ASSURANCE, SECURITY).
7. Новая сетевая зависимость (supply chain вне модели угроз).
8. Отключение гейта (`set -e` в обход, `|| true` вокруг build).
9. `SPARK_Mode => Off` в новом файле Tier A без одобрения.

## 4. Гейты (5 проверок перед каждым коммитом)

1. bare-metal build — 0 ошибок.
2. seL4 build — `Done`, без `[RT] ERROR`.
3. private overlay build — `Done`, без `[RT] ERROR`.
4. `verify.sh` — все VCs proved (гейт по ` (medium|high):` в stdout, а не по `not proved`).
5. `run_tests.sh` (QEMU) — все маркеры PASS.

Плюс быстрый `check_build_lists.sh` (ловит класс «модуль добавлен в один
список, а не в другой»). Один гейт упал — стоп, не коммить.

**Ловушка:** `Done: sel4_primary.iso` ≠ PASS. При ошибке Ada сборщик продолжает
и собирает ISO из старого ELF — ищи `[RT] ERROR` в выводе.

## 5. Отчётность: «что не смог» — всегда

ИИ склонен умалчивать провалы (это training objective). Поэтому в отчёте
пункт **«что не смог и почему»** обязателен на каждом уровне. Tier A (код с
контрактами) требует diff Pre/Post + unproved VCs **per-subprogram** (не
сумму) + список новых assume/annotate (если пусто — написать «пусто»).

## 6. Кейс: H61 — misaligned стек (чего НЕ поймал оракул)

Золотой пример границы «доказано ≠ работает». HMAC-SHA256 в FS-демоне был
**доказан** (gnatprove, Level 4). Но демон виснул молча: стек оказался
смещён на 8 байт, и `movaps`/`movdqa` (aligned SSE в SHA256) дал `#GP` →
тихий hang. gnatprove это не видит (выравнивание стека — вне модели SPARK);
тесты не ловят (hang молчаливый). Нашёл **человек** через систему маркеров
(`run_tests`-маркеры), локализовал по бинарному поиску, фикс — `andq $-16,
%rsp` в `fs_daemon.S`.

Урок: оракул доказывает *логику*; *среду исполнения* (стек, выравнивание,
тайминги, железо) он не видит. Поэтому конвейеру нужны оба — доказательство
(внутри модели) и маркеры/тесты (вне модели).

## 7. Другие кейсы (см. CHANGELOG + AUDIT_REGISTRY)

- **H82 (Persist silent fail):** `not-proved: 0` не значит «работает» — код
  проходил пруф, но NVMe `Is_Ready=False` и Init выходил молча.
- **C23/H33/H54 (Pre не enforced на Off-callers):** SPARK доказывает для
  Pre-вызовов, Off-caller не проверяет — нужен runtime guard.
- **M3/W11.1 (Vacuity):** gnatprove ловит недостижимый Pre, но не тавтологичный
  Post — вакуумные контракты ловит только ревью.

## 8. Правила для будущего инженера (выжимка)

1. Правило > задача. Конфликт — спроси, не решай.
2. Безопасность > функциональность. Сломанный гейт лучше зелёного с дырой.
3. Честный claim > красивый claim. «Private не готов» лучше «TCB доказан» с silent fail.
4. Существующий гейт > новый патч. Сначала починить build, потом новое.
5. Числа — только машинной генерации (метрики из канонического JSON, не из памяти).
